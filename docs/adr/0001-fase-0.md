# ADR 0001: decisões da Fase 0

| | |
|---|---|
| **Data** | 2026-11-01 |
| **Situação** | Decisões aceitas. Em 2026-11-01, o projeto considerou o portão validado no Windows e autorizou a Fase 1. macOS, GPU integrada e 120 Hz seguem sem medição (seção 2) |
| **Máquina das medições** | Uma só; ver a seção 3 e os limites listados lá |

## 1. Resumo

A Fase 0 existe para confirmar ou derrubar a stack com números, antes de construir o produto.

**No Windows, a stack se sustenta.** Rust, Tauri 2, WebView2, PDFium em processos isolados e
foliate-js atrás de um adaptador cumpriram as metas que deu para medir, com três ressalvas:
seções de livro muito longas passam da meta de relayout, um PDF escaneado passa um pouco da meta
de RAM durante a leitura, e nada foi medido em uma tela de 120 Hz.

**O portão foi aceito só para o Windows.** O critério original também exige macOS, GPU integrada e
tela de 120 Hz, e nenhum dos três existe na máquina usada. Esses itens não foram cumpridos: eles seguem
sem medição. Pelo critério do plano, nada aqui autoriza trocar a interface para Qt, mas também nada
prova ainda que o macOS não obrigue a isso.

**A Fase 1 foi autorizada nessa condição.** Ela constrói indexador, SQLite e CLI, sem interface, e o
plano mantém esse núcleo em Rust em qualquer desfecho. Os itens pendentes pesam é na Fase 2, que
investe no compositor.

Três resultados mudaram decisões e merecem atenção de quem for mexer nessas áreas:

1. **A origem do livro é uma barreira de segurança, não um detalhe.** O Tauri trata
   `http://book.localhost` como origem local. Servido de lá, um script dentro de um EPUB chamou
   um comando do app e encerrou o processo. Com um sufixo aleatório, a mesma chamada é recusada
   (D3).
2. **Um Worker recebe o SharedBuffer do WebView2 como memória viva.** Isso contraria a premissa
   inicial do Experimento B e dá o caminho de entrega mais rápido, mas a Microsoft não documenta
   esse comportamento (D1).
3. **O PDFium pré-compilado impede desligar o win32k.** É a maior superfície de ataque que sobra
   no sandbox, e só uma build própria resolve (D2).

## 4. Decisões

### D1. Entrega de pixels: Caminho C, depois B, depois A

**Contexto.** O ponto em aberto do plano era como um tile chega ao Worker do compositor. A premissa
de partida dizia que o SharedBuffer do WebView2 só existe na thread principal e não se transfere.
O teste no runtime real mostrou o contrário: o Worker não tem `chrome.webview`, mas o `ArrayBuffer`
se transfere e continua sendo memória compartilhada viva, nos dois sentidos.

| Caminho | Como o tile chega ao Worker | Precisa de |
|---|---|---|
| C | Lê onde o PDFium escreveu, sem cópia na CPU | Comportamento não documentado do WebView2 |
| B | A thread principal copia para um anel de `SharedArrayBuffer` | Isolamento de origem |
| A | `fetch` no protocolo `tile://` | Nada além do protocolo |

**Decisão.** O app testa o runtime a cada início, em buffers pequenos e separados, e usa o melhor
caminho que funcionar. A verificação é repetida a cada início porque o runtime do WebView2 se atualiza
sozinho. Um caminho que falhe ao abrir a sessão passa a vez ao seguinte. Um documento corrompido não
troca de caminho, porque falharia em todos.

**Evidência.** A tabela 5.1 traz as medições. `tools/test-cascade.mjs` simula cada falha em um WebView2
real e exige que os tiles cheguem à tela pelo caminho esperado: os 11 casos passaram.

**Consequências.**

- Se a Microsoft mudar esse comportamento, o app recai no B sem intervenção. O caso de uma mudança que
  derrube o renderer durante o teste, em vez de falhar, não é tratado.
- Com a thread principal bloqueada por 60 ms a cada 200 ms, só o B piora: a entrega P95 vai de 26–27 ms
  para 32–78 ms, e a nitidez segue na meta. O C não muda, então uma interface pesada nunca atrasa um tile nele.
- **O A não cumpre a meta de nitidez** (133–147 ms) e é o único caminho previsto para macOS e Linux.
  Isso precisa ser medido lá antes de qualquer conclusão, porque o custo do `fetch` no WebKit é outro.

### D2. Sandbox do worker de PDF

**Contexto.** Quem interpreta bytes de terceiros roda sem rede e sem acesso a arquivos. O worker é
tratado como se já estivesse comprometido.

**Decisão.** Camadas independentes, porque cada uma tem brechas que as outras cobrem:

| Camada | O que impede |
|---|---|
| Token restrito: grupos só para negar, único SID restritivo é o NULL SID, nenhum privilégio | Abrir qualquer coisa por nome: arquivos, pipes, registro, sockets |
| Integridade baixa | Escrever em qualquer coisa do usuário |
| Mitigações de processo: sem código dinâmico, CFG, ASLR forçado, verificação estrita de handles, sem pontos de extensão, sem fontes fora do sistema, sem imagens remotas ou de baixa integridade, sem FSCTL | Gerar e carregar código |
| Job por worker: 1 processo, limite de memória, morre com o host, sem clipboard nem handles USER externos | Processos filhos, esgotamento de memória |
| Estação de janelas e desktop próprios | Ler a tela e mandar entrada para as janelas do usuário |

O token final não consegue nem carregar uma DLL. Por isso o processo nasce suspenso e sua thread
principal recebe um token de inicialização mais capaz. O worker carrega o PDFium, entra em lockdown
(`RevertToSelf`) e só então lê a primeira mensagem do host. Nada que vem do documento roda com mais do
que o token final. O host confere isso quando o worker anuncia que está pronto, e o encerra se ele ainda
tiver o token de inicialização. Se o sandbox não puder ser criado, o worker não sobe.

**Alternativas descartadas.**

- *Só integridade baixa:* não impede leitura de arquivos nem rede.
- *AppContainer:* mantém leitura de `System32` e exigiria dar acesso ao `pdfium.dll` em disco, além de
  criar um perfil persistente. O token restrito nega tudo sem deixar rastro.
- *Fechar todo handle aberto na inicialização:* uma DLL do sistema que usasse um handle fechado derrubaria
  o processo, por causa da verificação estrita. Só as chaves predefinidas de registro são fechadas, porque
  isso esvazia um cache e tem efeito previsível.

**Evidência.** `crates/musaeum-render-pdf/tests/sandbox.rs`, com processos e PDFium reais:

- `sandbox-probe` se comporta como um worker comprometido e faz 33 tentativas. Todas são negadas: ler o
  próprio documento pelo caminho, `win.ini`, `kernel32.dll` e fontes do sistema; criar arquivos; abrir
  volume e disco; `LoadLibrary`; TCP e UDP; abrir `\Device\Afd`, `\Device\Tcp` e `\Device\Nsi` direto
  pelo kernel; criar processos; abrir o host, pipes, seções e eventos nomeados; registro; desktop do
  usuário, tela e clipboard; memória executável.
- 23 dessas tentativas têm controle: fora do sandbox, a mesma tentativa precisa funcionar. Sem isso, uma
  tentativa que falha por outro motivo pareceria proteção.
- O mesmo probe renderiza usando só os handles duplicados pelo host.
- O kernel confirma, de fora, o token, o job e as mitigações do worker real.
- A tabela de handles do processo é auditada. Dos que alcançam dados, só há 3 pipes, o documento somente
  leitura e o slab. Sobram chaves de registro do sistema em leitura e diretórios só para travessia, e nenhum
  handle aponta para processo, token, hive do usuário ou `WinSta0`.
- Os tiles saem idênticos, pixel a pixel, dentro e fora do sandbox, em uma página por fonte não embutida.

**Custo.** Nenhum mensurável (tabela 5.3). Os testes de worker e de pool agora rodam todos sob o sandbox.

**Riscos que continuam.**

- **win32k segue acessível.** `pdfium.dll` importa `user32.dll`, e isso impede desligar o win32k: na criação
  o carregamento falha (erro 1359), e depois de carregado o sistema recusa (erro 5). É a principal rota de
  fuga que sobra. O caminho é uma build própria do PDFium com essas importações em carga adiada e um
  provedor de fontes sem GDI, a fazer antes da 1.0.
- Volumes sem ACL, como exFAT em pen drive, não foram testados. O token não tem o privilégio de atravessar
  diretórios, o que deve bloqueá-los, mas isso é dedução, não medição.
- Portas ALPC e RPC não entram nas tentativas. O token restrito deve negar a maioria.
- O slab é compartilhado entre os workers, então um worker comprometido pode corromper os pixels dos outros.
  O que ele consegue ler se limita a esses pixels e ao documento aberto.
- Testado só no Windows 11 build 28000.

### D3. Isolamento do leitor fluido

**Contexto.** O foliate-js monta cada seção como um documento `blob:` na mesma origem do leitor e avisa, no
próprio README, que usá-lo sem CSP é perigoso.

**Decisão.** Três barreiras independentes:

1. **CSP com nonce**, em um cabeçalho que cobre o leitor e todas as seções, porque um `blob:` herda a política
   de quem o criou. `script-src` só tem o nonce, sem `'self'`: um `'self'` deixaria uma seção carregar os
   scripts do próprio app. `connect-src 'self'`, `frame-src blob:`, e `none` para o resto.
2. **Sandbox dos iframes das seções, sem `allow-scripts`.** Exigiu a única alteração no foliate-js. Não vale no
   WebKit, onde um bug obriga a manter `allow-scripts`, e lá só a CSP protege.
3. **Origem própria por livro**, `http://book.<128 bits aleatórios>.localhost`.

**O que a terceira barreira descobriu.** No WebView2, os scripts de inicialização do Tauri rodam em todos os
frames. Um script dentro de um livro encontra o `__TAURI_INTERNALS__` real, com a chave de invocação. A única
coisa que separa esse script dos comandos do app é a ACL do Tauri, e ela trata como **local** a origem
`<protocolo>.localhost` de um protocolo registrado:

| Origem do livro | Resultado de `__TAURI_INTERNALS__.invoke('bench_fail', ...)` com todas as outras barreiras desligadas |
|---|---|
| `http://book.localhost` | **Aceito: o app encerrou**, com a mensagem escrita pelo livro |
| `http://book.<aleatório>.localhost` | Recusado: `Command bench_fail not allowed by ACL` |

**Nunca sirva conteúdo de terceiros de `<protocolo>.localhost`.** Vale também para capas, notas e qualquer
visualização futura.

**Evidência.** `tools/test-epub-security.mjs` abre no app real um EPUB com 39 seções hostis: 19 formas de rodar script
e 20 de sair para a rede sem script. Um servidor canário fora do app registra o que escapa.

| Barreiras ligadas | Seções carregadas | Scripts que rodaram | Saídas de rede sem script |
|---|---:|---:|---:|
| CSP e sandbox do iframe, o que vai no produto | 39 de 39 | 0 | 0 |
| Só a CSP, a situação do WebKit | 39 de 39 | 0 | 0 |
| Só o sandbox do iframe | 39 de 39 | 0 | 16 |
| Nenhuma, o controle | 39 de 39 | 15 | 17 |

O sandbox sozinho barra scripts, mas não imagens e afins, e por isso a CSP é indispensável. O controle mostra que os
ataques funcionam. Quatro formas de rodar script não funcionaram nem nele (`<script type="module">`, `onfocus`
com `autofocus`, `meta refresh` para `javascript:` e `form` com ação `javascript:`), então o teste não diz nada
sobre elas. Nenhuma tem como passar pela CSP, mas isso é dedução.

Mesmo sem nenhuma barreira, um script dentro do livro não alcança o documento do app, nem o protocolo `tile://`,
nem os comandos do app, por nenhuma das rotas tentadas, inclusive enviando mensagem de IPC com a chave roubada.

**Riscos que continuam.**

- A proteção da IPC depende de uma regra interna do Tauri. O teste de controle pega uma mudança nela, então ele
  precisa rodar a cada atualização do Tauri.
- O leitor e as seções dividem a origem, então um script que escapasse tomaria o leitor. A página principal trata
  tudo que vem do leitor como não confiável, e os comandos alcançáveis por essa via só existem em benchmark.
- Abrir links externos ainda não existe. Isso vai precisar de confirmação do usuário, na Fase 3.
- Nada disso foi testado no WebKit.

### D4. foliate-js versionado, atrás de um adaptador

**Decisão.** Só `epub.js`, `epubcfi.js`, `paginator.js` e o `zip.js` entram no repositório, fixados em um commit, com a
alteração documentada em `vendor/foliate-js/README.md`. `apps/desktop/src/reader/foliate-adapter.ts` é o único arquivo que
os importa. `view.js` fica de fora, porque traz detecção de formatos que o plano entrega ao normalizador em Rust.

**Evidência.** O EPUB grande e 3 livros reais do Projeto Gutenberg abrem em 49 a 397 ms.

### D5. Seções longas precisam ser divididas

**Contexto.** O foliate-js faz o layout de uma seção por vez, então o custo de mudar a fonte depende do tamanho da seção, e
não do tamanho do livro.

**Evidência.** Tabela 5.4. Com até 200 KiB por seção, todas as mudanças ficam em até 65 ms. Com 400 KiB, mudar a fonte ainda cabe
(60–81 ms), mas redimensionar fica no limite (até 109 ms). De 1 MiB em diante, a meta não vale. Nos 3 livros reais, a maior seção tem
164 KiB, e a meta foi cumprida em todas as mudanças.

**Decisão.** O normalizador da Fase 3 divide seções acima de 200 KiB em limites de elemento. Sem isso, um romance inteiro em
um único XHTML leva quase um segundo para refluir ao mudar a fonte. O crossfade previsto no plano continua necessário.

### D6. Orçamento de memória

**Contexto.** A primeira medição deu 423 a 666 MB com um PDF aberto. O maior consumo era o processo de GPU, com 330 MB,
porque o array fixo de 256 camadas ocupa memória de processo além da GPU. O segundo eram os workers, com até 43 MB cada um
depois de ler um PDF escaneado.

**Decisão.**

- O número de camadas segue o tamanho da tela: 4 telas de tiles, entre 64 e 256. São 80 em 1080p.
- Cada worker mantém 3 páginas abertas em vez de 8.
- O padrão é metade dos núcleos lógicos, com no máximo 4 workers. Com 6, a fluidez não melhorou (tabela 5.3).
- Depois de 2 s sem trabalho, os workers fecham as páginas e devolvem a memória ao sistema.

**Evidência.** Tabela 5.5. Com um PDF escaneado, lendo, o total caiu de 666 para 257 MB. Com um vetorial, de 482 para 244 MB.
Retomar a leitura depois da pausa não teve custo visível: ao rolar de novo após 3 s parado, com 40 a 43 tiles novos, nenhum quadro
ficou só na cor do papel, e a nitidez P95 foi de 13 ms, a mesma da rolagem sem pausa.

**Nota de método.** O amostrador de memória só roda no cenário de memória. Ligado também nos outros, houve pausas de até 500 ms nos
quadros, que sumiram ao restringi-lo. A causa provável é o custo de ler o conjunto de trabalho privado de outro processo, mas isso
não foi isolado.

**Riscos que continuam.**

- Em uma tela 4K, as camadas sobem para 216, cerca de 136 MB a mais. A estimativa é que um PDF aberto passe de 250 MB
  nessa tela. Isso não foi medido.
- A memória da GPU integrada não aparece nesta soma de forma comparável, e não há GPU integrada para medir.

### D7. Licenças

**Decisão.** `deny.toml` lista as licenças aceitas, e qualquer outra reprova a verificação. Ficam de fora, entre outras, GPL-2.0-only,
AGPL, SSPL e licenças não comerciais. `tools/check-licenses.mjs` cobre crates, pacotes npm e o que entra sem gerenciador de pacotes,
listado em `vendor/third-party.json`. Ela roda no hook de `.githooks` quando uma dependência muda, e no CI.

**Evidência.** 328 crates, 94 pacotes npm (1 distribuído, 93 só de desenvolvimento) e 19 componentes vendorizados passam. Tirar o
MIT da lista fez a verificação falhar, então ela de fato reprova. O banco de avisos do RustSec não acusou nada.

**A revisar antes de distribuir.** Isto não é parecer jurídico.

- O runtime do WebView2 é proprietário. Está sendo tratado como biblioteca de sistema da GPLv3, o que é simples no Windows 11 e menos
  claro no Windows 10, onde ele pode precisar de instalação à parte.
- `webview2-com-sys` declara MIT, mas traz o `WebView2Loader` da Microsoft, que tem licença própria no estilo BSD. O `cargo-deny` não vê isso.
- O instalador precisa levar os avisos de `vendor/pdfium/*/licenses/`. FreeType e libjpeg-turbo pedem crédito na documentação.

### D8. Repositório

**Decisão.** Git local, ramo `main`, com finais de linha em LF em todos os sistemas. Ficam fora do Git os binários baixados, as fixtures geradas
e os resultados de medição. `.github/workflows/ci.yml` roda testes, lint e licenças no Windows.

**Consequência.** O workflow nunca foi executado, porque não há remoto. macOS e Linux entram nele quando o código rodar lá.

## 5. Métricas

### 5.1 Layout fixo, por caminho

### 5.2 Sem vsync

Mostra capacidade, não a cadência em uma tela de 120 Hz.

| Caminho | FPS | Intervalo P99 (ms) | Maior intervalo depois de abrir (ms) | Trabalho P99 (ms) |
|---|---:|---:|---:|---:|
| A | 3.326–3.372 | 1,15–1,20 | 7,6–7,9 | 0,05 |
| B | 3.398–3.565 | 0,94–1,50 | 8,0–9,3 | 0,05 |
| C | 3.338–3.390 | 1,65–1,77 | 3,9–4,7 | 0,07–0,12 |

Este número é sensível ao que mais roda na máquina. Com um jogo aberto, o mesmo teste no Caminho C deu 1.443–1.608 FPS e P99 de
3,2–4,2 ms. Por isso a seção 7 pede a máquina livre.
