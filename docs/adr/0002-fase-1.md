# ADR 0002: decisões da Fase 1

| | |
|---|---|
| **Data** | 2026-11-01 |
| **Situação** | Decisões aceitas. Em 2026-11-02, o projeto auditou e aprovou a Fase 1 e autorizou a Fase 2, Parte 1 |
| **Máquina das medições** | A mesma da Fase 0: Ryzen 5 5600G, 31 GB, SSD NVMe de 1 TB, Windows 11, com o Microsoft Defender ativo |

## 1. Resumo

O núcleo sem interface existe e funciona pela linha de comando: SQLite, reconhecimento de arquivos,
indexador, diário de operações em disco e busca. Os sete cenários da bateria passam, 100 mil arquivos
reais são indexados em 2,7 minutos e nenhuma tecla passou de 23 ms na busca, contra a meta de 30 ms.

Seis resultados mudaram o que foi construído, e merecem atenção de quem for mexer nessas áreas:

1. **Os cinco passos do plano não bastam para o safe save.** Salvar por substituição deixa um arquivo
   diferente no mesmo caminho, e por aqueles passos um livro editado viraria um documento novo. A bateria
   exige o contrário, então existe uma regra a mais (D2). É o único desvio do plano.
2. **O `notify` para de vigiar em silêncio quando o buffer do sistema estoura.** É justamente o caso
   que o watcher precisa cobrir, então o Musaeum tem um watcher próprio, que avisa (D6).
3. **`mmap` e checkpoint no commit derrubavam a busca e a indexação.** Com eles, uma tecla chegou a
   1,66 s, e indexar levava 17 minutos. Sem eles, 23 ms e 2,7 minutos (D8).
4. **`FILE_FLAG_OPEN_NO_RECALL` não impede o download de um placeholder.** A barreira que parecia a óbvia
   não existe, e quem protege é a verificação dos atributos (D5).
5. **Um único nome não-Unicode na Lixeira quebra a leitura dela inteira.** E caminhos longos entram na
   Lixeira e não saem. O diário agora recusa os dois de antemão (D9).
6. **Enquanto um arquivo é lido, o Windows não deixa renomear a pasta dele,** mesmo com `FILE_SHARE_DELETE`.
   É o custo que sobra do hash em segundo plano (seção 6).

## 2. Portão de saída

Do roteiro: bateria automática sem perda de identidade, 100 mil arquivos indexados. Da seção 2.8: busca
em metadados, 100 mil obras, até 30 ms por tecla.

Em cada cenário, "identidade mantida" quer dizer que obra, documento, revisão e instância continuam os
mesmos, e que uma anotação e uma avaliação continuam lá.

| Cenário | Como foi testado | Resultado |
|---|---|---|
| Renomear arquivo | Real, em NTFS. Com o arquivo aberto em modo exclusivo durante a varredura, então qualquer leitura falharia | Identidade mantida, 0 arquivos abertos, 0 bytes lidos |
| Mover pasta inteira | Real, 200 arquivos. Comparação linha a linha das tabelas antes e depois | Muda 1 linha de `folder` e 0 de `file_instance`, 0 bytes lidos |
| Trocar de volume | **Real:** imagem ISO montada sem letra de unidade, com serial próprio e sistema de arquivos CDFS. Também simulado em NTFS, com o serial trocado | Reconhecido pelo BLAKE3 completo. Volume desmontado não vira ausente |
| Safe save | Real, de três formas: renomear sobre o alvo, `ReplaceFile`, e apagar seguido de renomear | Nova revisão do mesmo documento, com o vínculo com a anterior. Os mesmos bytes não criam revisão |
| Restaurar ausente | Real: pela Lixeira de verdade, movendo para fora da raiz e de volta, e por cópia de backup | Mesmo ID: sem ler nada. Cópia: confirmada pelo hash completo, na mesma linha de antes |
| Placeholder de nuvem | **Real:** sync root registrada com a Cloud Filter API, a mesma do OneDrive. O teste é o provedor e conta cada pedido de bytes | 0 pedidos ao varrer, mover ou renomear. O controle lê de propósito e o pedido aparece. O hash vem depois que o arquivo fica local |
| Mudanças com o app fechado | Real: renomear, mover, editar, safe save, apagar, renomear pasta, recriar e adicionar, tudo de uma vez | Tudo reconhecido na abertura seguinte |
| 100 mil arquivos indexados | Arquivos reais: 80 mil EPUBs e 20 mil PDFs, 891 MiB | Todos indexados, todos com hash e metadados, 0 recusados |
| Busca ≤ 30 ms por tecla | 22.947 teclas em 9 classes de consulta, com o escritor parado e ocupado | P99 de 11–12 ms, máximo de 23 ms, 0 acima da meta |

Além dos cenários do portão, a bateria cobre outros casos, com testes para cada um: passos 2 e 4, File ID reutilizado
(simulado, como no volume em NTFS), duplicatas, hard links, troca de nomes entre dois arquivos, raiz
indisponível, junções, caminhos longos, nomes não-Unicode e arquivos em uso.

**Testes.** 389 em Rust no workspace, 275 deles novos. Todos passam, com `clippy -D warnings` e `fmt` limpos, e
uma rodada completa não deixa nada no `%TEMP%` nem na Lixeira.

## 3. Como foi medido

O `tools/library-bench` gera os livros como arquivos de verdade: cada um tem bytes próprios, e 1 em cada
100 tem 512 KiB. As palavras dos títulos são sorteadas com a assimetria das palavras reais, em vários
idiomas e com cirílico, porque são as palavras comuns que deixam a busca lenta. Três classes de consulta
buscam de propósito o pior caso: fragmentos muito comuns, pares de palavras muito comuns e nada que exista.

Os limites do que isso mede:

- **O corpus de escala é sintético.** Os 3 EPUBs reais do Project Gutenberg foram lidos corretamente, com
  título, autor, idioma, data e `dc:identifier`. Nenhum PDF real passou pelo leitor de `/ID`.
- **O Defender estava ativo,** como na máquina de quem vai usar. Exclusões não foram configuradas.
- **Uma máquina só.** A máquina de referência do plano, com GPU integrada, não existe aqui, e a busca
  depende do processador.
- **Cache frio não foi medido.** Sem administrador não dá para esvaziar o cache do sistema, e os arquivos
  estavam recém-gerados.

## 4. Decisões

### D1. Dois bancos, um escritor por construção

**Decisão.** `library.db` guarda o insubstituível e tem `synchronous=FULL`. `cache.db` guarda o que dá para
refazer e tem `NORMAL`. Toda escrita passa por uma única thread, dona da única conexão que escreve, e um
arquivo de lock impede dois processos de serem o escritor. Quem só consulta abre em modo leitura.

**Por quê.** Com um escritor só, não há `SQLITE_BUSY` entre escritores para tratar. `FULL` custa 5 ms por
commit, e é o preço de uma anotação sobreviver a uma queda de energia.

**Tratamento de falhas.** Um `cache.db` corrompido ou de versão mais nova é recriado sem aviso. Um
`library.db` nas mesmas condições é um erro e fica intacto: esse arquivo não é nosso para substituir.

**Backups.** Automáticos, verificados a cada hora enquanto o indexador roda e ao fim de `musaeum reconcile`: uma cópia
por dia, guardando as de 7 dias e as de 4 semanas, mais as 3 últimas feitas antes de uma atualização de esquema. Um backup
só ganha o nome final depois do `integrity_check`, e restaurar deixa o banco substituído guardado, sem apagar.

**A garantia que não depende do código.** Triggers no banco recusam apagar uma revisão confirmada, uma
instância dela, uma anotação ou uma entrada do diário. Só uma revisão ainda não confirmada pode sumir.

### D2. Reconhecimento: os cinco passos, e mais um

**Decisão.** Os passos do plano, na ordem do plano, com uma regra entre o 2 e o 3:

> Um File ID diferente, em um caminho cujo arquivo estava lá até agora e não está em nenhum outro lugar,
> é uma nova revisão do mesmo documento.

**Por quê.** Salvar por substituição deixa outro arquivo naquele caminho. Pelo passo 3, seria um ID
desconhecido; sem candidato com os mesmos bytes, viraria um documento novo, e as anotações ficariam para
trás. Só que a bateria do próprio plano exige que isso não aconteça.

**O risco.** Trocar um livro por outro não relacionado com o mesmo nome, entre duas varreduras, também vira
revisão. As anotações continuam na revisão onde foram feitas, então nada se perde. Só um arquivo que
*estava presente* recebe isso: se ele já tinha sumido em uma varredura anterior, o que aparecer naquele caminho
vira documento novo, com uma sugestão.

**A ordem importa além do que o plano diz.** O passo 1 roda sobre tudo o que a varredura viu antes de qualquer
conclusão, e tudo em uma transação. Assim, um arquivo que se moveu já saiu do caminho antes de alguém
olhar para o que apareceu no lugar dele, dois arquivos podem trocar de nome, e ninguém vê como ausente um
arquivo que só estava mudando de lugar.

### D3. Revisão não confirmada

**Decisão.** Um arquivo novo vira na hora obra, documento, revisão e instância, com `blake3` nulo. Quando o hash
completo chega, se os bytes já são conhecidos, a linha provisória é absorvida pela revisão existente,
levando junto o que alguém tenha feito nela no meio tempo.

**Por quê.** É o que o plano pede: a biblioteca já funciona enquanto o hash é calculado. O fingerprint rápido
não decide nada: só coloca os candidatos primeiro na fila, porque até o hash chegar eles aparecem como documentos
novos, o que está errado. Enquanto nada foi confirmado sobre os bytes, mudar o arquivo atualiza a própria
revisão, então uma cópia grande em andamento não deixa um rastro de revisões.

### D4. Parser só no processo `ingest`

**Decisão.** Ler `/ID[0]` e `dc:identifier` é interpretar bytes hostis, então, pela regra de segurança do plano,
isso roda em um processo sem rede e sem abrir arquivo por caminho, que recebe cada livro como um handle. O Core
nunca interpreta o conteúdo de um livro, e o módulo de parsers não tem nenhum `unsafe`.

**Política mais rígida que a do PDFium.** Sem `pdfium.dll` para atrapalhar, este worker roda com o win32k
desligado e só carrega DLLs assinadas pela Microsoft. O teste lê essas políticas de volta do kernel.

**A resposta do worker também é hostil.** O host limita o tamanho das mensagens antes de alocar, corta cada
campo no que ele pode ser, e mata o worker que trava, cai ou fala bobagem, o que custa os metadados daquele
livro e nada mais. Sem worker disponível, tudo funciona, e os metadados vêm depois.

### D5. Nuvem: só os atributos protegem

**Decisão.** A listagem usa `FileIdExtdDirectoryInfo`, que traz ID, tamanho, data e atributos do próprio diretório,
então uma varredura não abre nenhum arquivo. Para ler, os atributos são verificados antes de abrir e de novo
pelo handle.

**O que os testes derrubaram.** Eu tinha documentado `FILE_FLAG_OPEN_NO_RECALL` como segunda barreira. Com um
provedor real, ler por esse handle dispara o download do mesmo jeito. O que fecha a janela entre a verificação e a
leitura é outra coisa, também testada: com o arquivo aberto, o Windows recusa liberar os bytes dele.

### D6. Watcher próprio, em vez do `notify`

**Decisão.** Um `ReadDirectoryChangesW` em `musaeum-fs`, com cerca de 270 linhas, que informa o overflow e a perda do
watch como eventos.

**Por quê.** No `notify` 8.2.1, `ERROR_NOTIFY_ENUM_DIR` não tem tratamento próprio, e em erro desconhecido ele para
de vigiar a pasta sem avisar. Isso foi lido no código dele, e o código de erro foi confirmado aqui: um overflow
real termina com 0 bytes e erro 1022. O overflow é testado de verdade, com um buffer menor que qualquer registro.

**O custo.** macOS e Linux vão precisar de uma implementação própria, que pode ser o `notify` se ele tiver
corrigido isso até lá.

**Eventos são só pistas.** Um evento só marca um diretório para olhar. Quem decide é a mesma reconciliação da
primeira varredura. O overflow pede uma varredura inteira, e o relógio faz uma a cada 15 minutos de qualquer jeito.

### D7. Busca em três camadas, sem ordenar por relevância

**Decisão.** Até três consultas por tecla, parando quando há resultados suficientes: o título começa com o que
foi digitado; cada palavra digitada começa uma palavra em algum lugar; cada palavra aparece no meio de uma
(trigramas).

**Por quê.** `ORDER BY rank` precisa olhar todas as obras que casam, e é isso que estoura o orçamento na primeira
letra. As camadas já são uma ordem de relevância, e dentro de cada uma vai o título mais curto primeiro.

### D8. Leitores sem `mmap`, checkpoint fora do commit

**Decisão.** Os leitores não mapeiam o banco em memória. O commit não faz checkpoint: uma thread de baixa
prioridade faz, sem segurar o escritor. Só quando o log passa de 64 MiB o próprio escritor para e o encerra, entre
uma escrita e outra.

**Evidência.** Comparando o código antes e depois, com as mesmas 100 mil obras:

| Com o escritor ocupado | Antes | Depois |
|---|---|---|
| Busca: tecla mais lenta | 975–1.664 ms | 16–24 ms |
| Busca: teclas acima de 30 ms | 82–92 | 0 |
| Commit: P99 | 600 ms | 8,4 ms |
| Varredura inicial | 226 s | 36 s |
| Hash e metadados | 775–785 s | 127 s |

Para isolar a causa, um experimento separado ligou e desligou cada variável, por 25 s cada uma:

| Durabilidade, `mmap`, checkpoint | Leitura mais lenta | Leituras > 30 ms | Commit P99 |
|---|---|---|---|
| FULL, ligado, no commit | 501 ms | 4 | 483 ms |
| FULL, **desligado**, no commit | 3,9 ms | 0 | 425 ms |
| FULL, ligado, **fora do commit** | 209 ms | 2 | 13,7 ms |

**O que não foi isolado.** O mecanismo dentro do Windows. O que está demonstrado é o efeito: com `mmap`, leituras
travam durante o checkpoint, e sem ele, não. A busca também não ficou mais lenta sem ele.

**Um bug no caminho.** A primeira versão do checkpoint, fora do commit, usava `RESTART` na thread de baixa prioridade.
Isso segurou o lock de escrita por tempo suficiente para o escritor desistir, e o teste de carga falhou com
`database is locked`. É por isso que encerrar o log é trabalho do escritor.

### D9. Diário e Lixeira

**Decisão.** A intenção é gravada antes de tocar no disco, e o resultado, junto com o que ele significa para a
biblioteca, depois. Na abertura, cada entrada sem desfecho é resolvida olhando o disco. Mover nunca sobrescreve e
apagar é sempre mandar para a Lixeira.

**O diário recusa de antemão o que não conseguiria desfazer.** Todos estes casos foram descobertos pelos testes:

| Caso | O que aconteceria | O que o diário faz |
|---|---|---|
| Caminho com mais de 259 caracteres | Entra na Lixeira e a restauração falha | Recusa |
| Nome não-Unicode | `trash::os_limited::list` passa a falhar para a Lixeira **inteira** | Recusa |
| Lixeira ilegível, por causa de um nome assim vindo de outro programa | Não haveria como desfazer | Recusa |
| Volume sem Lixeira, como um pendrive | O shell apagaria de vez | Recusa |

**Restaurar deixa um registro `$I` órfão,** e o diário o remove depois de restaurar.

### D10. "Assíncrono" são threads, não um runtime

**Decisão.** Threads e canais, sem `tokio`.

**Por quê.** Quase todo o trabalho é E/S de arquivo, para a qual um runtime assíncrono no Windows só usaria um pool de
threads, e o que o plano pede é que nada faça o resto do programa esperar. Leitura de arquivo roda em
`THREAD_MODE_BACKGROUND_BEGIN`, que nesta máquina ociosa não custou nada: 163 s, contra 160 s em prioridade normal.

### D11. Dependências novas

`rusqlite` com SQLite embutido (MIT), `blake3` (CC0 ou Apache-2.0), `quick-xml` (MIT) e `trash` (MIT). Todas passam
pelo `deny.toml`. A CLI analisa os argumentos à mão, como o resto do projeto.

seguinte termina com tudo certo e nada contado duas vezes.

## 6. Limitações conhecidas

**Comportamento que alguém vai encontrar:**

- **Renomear uma pasta pode falhar enquanto um arquivo dela está sendo lido.** O Explorer diz que a pasta está em uso.
  Durante a primeira indexação isso pode acontecer em qualquer pasta, por instantes. Tentar de novo resolve.
- **Mover entre volumes pelo diário é recusado.** Exigiria copiar, verificar e apagar, o que não foi construído. Mover
  por fora, com o Explorer, é reconhecido normalmente.
- **Substring exige 3 caracteres por palavra.** Com menos, só o começo de palavra funciona, o que limita buscas de
  2 caracteres em japonês e chinês.
- **Um arquivo temporário com extensão de livro** que dure mais que o tempo de espera e depois seja renomeado sobre o
  original vira um documento novo, com uma sugestão, em vez de uma revisão.
- **Um PDF só tem título pelo nome do arquivo.** Ler `/Info` fica para quando o `ingest` usar o PDFium.

**Limites do reconhecimento, por decisão do plano:**

- **Alterar um arquivo mantendo tamanho, data e ID não é detectado,** porque o passo 1 não lê o arquivo.
- **Um arquivo movido e editado com o app fechado** vira documento novo, com uma sugestão. O plano é explícito ao dizer
  que o File ID sozinho não prova nada.
- **Um hard link alterado pelo outro nome** só é percebido quando o diretório atualizar a entrada.

**O que não foi testado:**

| Item | Situação |
|---|---|
| ReFS | Os 128 bits são guardados e comparados, mas só rodou em NTFS, que usa 64. Sem volume ReFS aqui |
| Troca entre dois volumes NTFS | O volume real é CDFS, somente leitura, sem File IDs. Entre NTFS é simulado, com o serial trocado |
| exFAT, rede | O código trata volumes sem IDs duráveis, e o CDFS exercitou esse caminho. exFAT e rede em si, não |
| OneDrive de verdade | Mesma API e placeholders reais, mas o provedor é o teste |
| Diretório como placeholder | Listar pode trazer a lista de arquivos da nuvem, não os bytes. Sem teste |
| PDFs reais no leitor de `/ID` | Só sintéticos |
| Lixeira configurada para apagar na hora | Registraria um aviso depois do fato. Sem teste, para não mexer na configuração da máquina |
| Lixeira ilegível | A recusa está no código, sem teste: reproduzir exige colocar um item assim na Lixeira real |
| Worker sob as 33 tentativas do `sandbox.rs` | O `sandbox-probe` precisa do `user32`, então não roda com win32k desligado. Token e job são os mesmos do `Lockdown`, e as mitigações são lidas do kernel |
| Crash no meio de uma operação do diário | Injetado por SQL, cobrindo cada estado possível. O processo morto de verdade é só no meio da varredura e do hash |
| Migração real | O mecanismo é testado com migrações de exemplo. Ainda só existe a versão 1 |
| CI | Continua nunca executado. `cloud.rs` e `real_volume.rs` podem exigir ajuste nos runners |
| macOS e Linux | O código só compila no Windows |

## 7. Como reproduzir

```powershell
cargo test --workspace
cargo clippy --workspace --all-targets -- -D warnings

cargo build --release -p library-bench -p musaeum-library -p musaeum-cli
.\target\release\library-bench.exe
```

O benchmark escreve em `bench-results/library-100000.json`. Para repetir só a busca, rode uma vez com `--keep` e depois com
`--reuse`.
